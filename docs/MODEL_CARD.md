# Model card

## Purpose

Demonstrate a local maintenance application integrating descriptive analytics, approved service schedules and dated multi-horizon risk estimates. The public demo is not the private project's fitted model or its performance report.

## Training data and simulation

All assets, stations, sensor values and events are fictional, generated by `tools/generate_demo.py` with seed 314159. A latent degradation state drifts upwards between interventions. Noisy inspection, temperature, vibration, load and applicable pressure readings reflect that state. Daily failure probability depends on the state plus a random draw. Completed work resets or reduces degradation. The classifier receives measured-style readings, not the latent state or random draw.

This simulation deliberately creates an association between condition and failure so the pipeline can be demonstrated. Good results on these rules do not prove usefulness on a real machine. Original workplace data, historical private models and private evaluation reports are excluded.

## Target and inputs

For 7, 14 and 30 days, predict at least one distinct breakdown episode strictly after an observation and within that horizon. Inactive equipment and windows without full follow-up coverage are excluded from training/evaluation. Follow-up work orders sharing a failure-event ID do not create a second target failure. Station, equipment class, operating state and condition/usage values are the fixed core predictors. Equipment ID, name, record-source label and future outcomes are excluded.

## Method

Each horizon uses a fixed 80-tree GradientBoostingClassifier pipeline with median numeric imputation, missing indicators and one-hot categorical encoding fitted only on training dates. A later calibration period fits a positive-slope sigmoid map; identity is retained if that map would reverse ranking. A separate validation period selects the highest threshold reaching at least 80% recall. This is the one offered alert policy. Calibration and validation outcome windows end before the next period starts. Final test dates are excluded from fitting and threshold selection.

Models use the fixed parameters in `tools/train_demo.py`; no optimization search or equipment-transfer result is claimed. A predetermined cumulative-maximum projection enforces nondecreasing risk across horizons. Test metrics use the projected probabilities and frozen validation thresholds. They count overlapping equipment-observation windows, which may refer to the same event.

## Interpretation and limits

The output is a window probability. It is not an exact failure date, count of future failures, physical diagnosis, availability estimate or remaining useful life. Tree-path contributions explain the model's raw score, not causal effects. Sensor values and event frequency are imposed by simulation assumptions. There is no evidence of field calibration, unseen equipment reliability, real inspection cost savings or suitability for autonomous maintenance control.

The bundled readings have fixed historical dates. An updated clock does not create a new observation. Approved service intervals and measured cumulative-hour limits remain independent of the classifier. Low risk does not extend a due date. See the generated [evaluation](EVALUATION.md) and use real prospective validation before operational deployment.

The public release uses a fingerprint of generated CSV inputs. Both Excel copies are excluded, and retraining does not require a workbook. The existing fitted demo weights and measured metrics are unchanged by this packaging revision.
